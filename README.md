# Challenge — подходы к решению задач

React-интерфейс и Python-бэкенд для алгоритмических и аналитических задач через
DeepSeek в API OpenCode Go. Исходный раздел с двумя интенсивностями рассуждений и
пятью подходами к решению, отдельный раздел с тремя температурами генерации,
независимая история переписки и передача контекста модели. История сохраняется только в `localStorage`
браузера: без регистрации и базы данных. Для API нужны подписка Go и личный ключ Console.

## Режимы

Кнопка-бургер слева в шапке открывает левое меню с двумя разделами:
**«Подходы к решению»** и **«Температура»**. При открытии приложения выбран первый.
Переключение не перезагружает страницу и не отменяет ожидающие ответы. Выбор вкладок
каждого раздела сохраняется до перезагрузки. Меню закрывается выбором раздела,
кнопкой, Escape или нажатием на подложку; фокус возвращается бургеру.

В **«Температура»** только три вкладки и обычный прямой ответ:

| Вкладка | temperature |
| --- | --- |
| Низкая | `0` |
| Средняя (по умолчанию) | `0.7` |
| Высокая | `1.2` |

Здесь рассуждения явно отключены (`thinking.type: disabled`), effort не выбирается,
других подходов и автоматического сравнения температур нет. Один вопрос — один вызов.
Форма и структура вывода прежние: вопрос, дата, карточка «Ответ», длительность,
токены, ожидание и ошибки. В метаданных показаны температура и отключённые рассуждения.

В **«Подходы к решению»** всё как прежде. Сверху выбирается интенсивность рассуждений:

- **Минимум рассуждений** — `thinking.type: enabled`, `reasoning_effort: low`.
- **Максимум рассуждений** — `thinking.type: enabled`, `reasoning_effort: max`.

Выбор применяется к каждому обращению, включая генерацию промпта, все роли и четыре
подхода сравнения. Максимум может существенно увеличить задержку и расход токенов.
DeepSeek V4.1 Flash поддерживает `low`, `high`, `max`.
Источники: [каталог Go](https://opencode.ai/inference/go/v1/models) и
[Thinking Mode DeepSeek](https://api-docs.deepseek.com/guides/thinking_mode).

Под ними — пять вкладок подходов:

| Вкладка | Как работает | Обращений к модели |
| --- | --- | --- |
| Прямой ответ | Предыдущие сообщения и новый вопрос, без дополнительных инструкций по решению | 1 |
| Пошаговое решение | Объяснение подхода, шаги, проверка, итог | 1 |
| Промпт → решение | Генерация промпта, затем отправка его модели без изменений | 2 |
| Команда ролей | Аналитик → исполнитель → критик с самодостаточным исправленным итогом | 3 |
| Сравнение | Четыре независимых подхода на одном вопросе | 7 |

Созданный промпт, разбор аналитика и решение исполнителя доступны в раскрывающихся
блоках. Для каждого результата показаны время выполнения и фактический расход
токенов всех его этапов. Четыре подхода сравнения запускаются параллельно, но этапы
внутри одного подхода выполняются последовательно. Ошибка одного подхода не скрывает
остальные результаты.

У каждой пары **«интенсивность рассуждений / подход»** своя история и черновик:
десять исходных диалогов. В разделе «Температура» ещё три независимых диалога —
по одному для `0`, `0.7`, `1.2`, всего тринадцать. Черновики живут только в памяти
страницы и не восстанавливаются после перезагрузки. Вкладки и разделы не смешивают
истории и черновики. В сравнении у каждого подхода свой контекст
предыдущих сравнений, независимый от остальных вкладок и подходов. В следующий
запрос включаются все успешные вопросы и ответы этого подхода, в том числе
промежуточные этапы. Ошибки остаются видимыми в истории, но не отправляются как ответы
модели. История не обрезается автоматически.

**«Очистить историю»** из любого раздела удаляет вопросы и ответы всех тринадцати диалогов из памяти и
хранилища браузера, очищает черновики и отменяет ожидание текущих запросов, в том числе
в других открытых вкладках браузера этого же сайта. Поздний
ответ не восстановит удалённую переписку. Это не удаляет данные у внешнего провайдера
и не гарантирует остановку уже начатой им генерации. После перезагрузки страницы
незавершённые запросы помечаются как прерванные; автоматически они не повторяются.
Если браузер запрещает запись или его хранилище переполнено, интерфейс показывает
предупреждение и продолжает работать с историей в памяти.

Вкладки браузера синхронизируют историю через `storage` и при возвращении фокуса.
Запись выполняется под общей Web Lock с повторным чтением актуальной истории;
поколение диалога проверяется и перед применением ответа, даже если событие очистки
ещё не доставлено. Активные запросы удерживают отдельные блокировки: работающий
запрос другой вкладки не считается прерванным, а второй запрос в тот же диалог не
запускается. Без Web Locks (нужен HTTPS или localhost) новые сообщения остаются
только в памяти страницы, без небезопасной записи общей истории; показывается предупреждение.

UUID поколения хранится отдельно в `challenge.conversations.generation`. При очистке
он заменяется новым: после удаления переписки остаётся только UUID, без текста сообщений.
Он передаётся как `conversation_id`; бэкенд выводит из него отдельный Go session ID
для каждой интенсивности, вкладки и стратегии сравнения. Этот ID одинаков для всех
этапов и следующих вопросов, сохраняется после перезагрузки и меняется при очистке.

История хранится в `challenge.conversations.v3`. При отсутствии v3 история v2
переносится в прежние десять диалогов. Если нет и v2, история v1 открывается в
«Минимум рассуждений», а остальные диалоги остаются пустыми. У старых ответов
указано «До настройки effort»: им не приписывается новый параметр задним числом.
Текст, этапы, ошибки и UUID поколения сохраняются. Старые копии удаляются только
после успешной записи v3; при сбое записи остаются на месте. Существующая v3 имеет
приоритет, повреждение не вызывает скрытый откат к старой копии. Общая очистка
удаляет v1, v2 и v3, чтобы прежняя история не восстановилась.

После обновления приложения перезагрузите все старые открытые вкладки: совместная
запись старой и новой версий фронтенда не поддерживается. При откате старая сборка
не читает v3; не удаляйте её — данные снова станут доступны после обновления.
Автоматической обратной миграции в v2 нет. Очистка не удаляет данные у провайдера.

## Работа с OpenSpec

В репозитории настроен [OpenSpec](https://openspec.dev/docs) с профилем `core`
и интеграцией для OpenCode. Контекст и правила — в `openspec/config.yaml`,
спецификации — в `openspec/specs/`, активные изменения — в `openspec/changes/`.
Текущее поведение проекта (as-is) зафиксировано в основных спецификациях:

- [Подходы к решению и сравнение](openspec/specs/solving-strategies/spec.md).
- [API вопросов и проверка состояния](openspec/specs/question-api/spec.md).
- [Интеграция с моделью](openspec/specs/model-integration/spec.md).
- [История диалогов](openspec/specs/conversation-history/spec.md).
- [Веб-интерфейс](openspec/specs/web-interface/spec.md).
- [Запуск и размещение](openspec/specs/deployment/spec.md).

CLI можно установить без Node.js официальным установщиком (macOS/Linux):

```sh
curl -fsSL https://openspec.dev/cli/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
```

Интеграция сгенерирована OpenSpec **1.16.0**. Команды в OpenCode:

- `/opsx-explore` — изучить идею без реализации.
- `/opsx-propose <описание>` — подготовить предложение, спецификации, дизайн и задачи.
- `/opsx-update` — скорректировать план изменения.
- `/opsx-apply` — реализовать согласованные задачи.
- `/opsx-sync` — перенести изменения требований в основные спецификации.
- `/opsx-archive` — архивировать завершённое изменение и обновить спецификации.

Артефакты пишутся по-русски; структурные заголовки OpenSpec остаются на английском.
Команды CLI запускаются из корня репозитория:

```sh
openspec list
openspec validate --all --strict
openspec update
```

`openspec update` обновляет сгенерированные команды и навыки после обновления CLI.

## Локальный запуск

Из корня проекта, с установленным Python 3.15.2:

```sh
python3.15 -m venv .venv
source .venv/bin/activate
python -m pip install -e './backend[dev]'
python -m uvicorn app.main:create_app --factory --reload --host 127.0.0.1 --port 8000
```

В другом терминале, из `frontend/`:

```sh
npm ci
npm run dev
```

Откройте <http://127.0.0.1:5173>. Vite проксирует `/api` на бэкенд — браузер не
обращается к OpenCode Go напрямую. CORS с разрешением всех доменов не нужен.

## Сборка

Из `frontend/`:

```sh
npm run build
```

После сборки перезапустите бэкенд **без `--reload`**. Он отдаёт интерфейс из
`frontend/dist` по <http://127.0.0.1:8000>, а не из корня репозитория. `.env`
недоступен через HTTP. `npm run preview` предназначен только для просмотра статики:
для запросов к ИИ используйте Vite dev-сервер или собранный интерфейс на бэкенде.

## API

- `GET /api/health` — состояние приложения, без проверки ключа и обращения к OpenCode Go.
- `POST /api/ask` — вопрос, подход, effort **или** temperature, UUID диалога и история (примеры ниже).
- Вопрос должен быть непустым после удаления пробелов по краям. Приложение не ограничивает его длину; лимит контекста провайдера остаётся.
- `422` — неверный вопрос, режим, UUID или история; `429` — лимит запросов; `503` — проблема с ключом/доступом/балансом;
  `502` — ошибка провайдера; `504` — тайм-аут.

```json
{
  "question": "А какая сложность?",
  "mode": "direct",
  "effort": "low",
  "conversation_id": "2c904d3e-b129-48be-9528-1a3ddba32dc3",
  "history": {
    "direct": [
      {"role": "user", "content": "Найди максимум массива"},
      {"role": "assistant", "content": "Пройди массив, сохраняя наибольший элемент."}
    ]
  }
}
```

Подходы: `direct`, `steps`, `prompt`, `roles`, `compare`. По умолчанию — `direct`,
`effort: low`, история пустая. Допустимые effort — `low` и `max`. В одиночном режиме `history` может содержать только его ключ;
в сравнении — ключи четырёх подходов. Сообщения истории должны идти парами
`user` / `assistant`; системные сообщения от клиента не принимаются.
`conversation_id` нужно переиспользовать до очистки переписки. Для совместимости
поле необязательно: без него сервер создаёт UUID на один запрос и не сохраняет
стабильную Go-сессию между вопросами.

Наличие `temperature` выбирает отдельную ветку прямого ответа без рассуждений:

```json
{
  "question": "Объясни бинарный поиск",
  "mode": "direct",
  "temperature": 0.7,
  "conversation_id": "2c904d3e-b129-48be-9528-1a3ddba32dc3",
  "history": {}
}
```

Допустимы только числа `0`, `0.7`, `1.2`; ноль не заменяется средней температурой.
Строки, boolean, null и другие значения отклоняются. В этой ветке `mode` — только
`direct` (также по умолчанию), поле `effort` должно **отсутствовать**, даже null
запрещён. Несовместимые параметры дают 422 до вызова провайдера. Правила вопроса,
UUID и `history.direct` остаются прежними. Клиент не может передавать `thinking`.
В Go отправляются `thinking.type: disabled`, выбранная температура и `stream: false`,
без `reasoning_effort`. Ошибки обрабатываются тем же путём без повторов и подмены настроек.

Пример ответа:

```json
{
  "question": "А какая сложность?",
  "date": "2026-11-04T12:30:00Z",
  "mode": "direct",
  "effort": "low",
  "tokens": 142,
  "results": [{
    "mode": "direct",
    "answer": "O(n) по времени, O(1) дополнительной памяти.",
    "tokens": 142,
    "duration_ms": 1250,
    "stages": [],
    "error": null
  }]
}
```

В сравнении `results` содержит четыре результата в порядке `direct`, `steps`,
`prompt`, `roles`. У неуспешного подхода `answer` и `tokens` равны `null`, `error`
содержит безопасное сообщение, а `stages` — уже завершённые промежуточные этапы.
Общий `tokens` также `null`, если хотя бы один подход завершился ошибкой: неизвестный
полный расход не выдаётся за нулевой. Частичные ошибки сравнения возвращаются внутри
HTTP 200; ошибки запроса целиком и одиночного режима — соответствующим HTTP-статусом.

В температурном ответе оболочка и формат `results` те же, но `effort: null` и
добавлено обязательное поле `temperature` с фактическим значением запроса. Результат
единственный, `mode: direct`, `stages: []`. Прежние ответы без температуры по-прежнему
содержат ровно шесть полей: `question`, `date`, `mode`, `effort`, `tokens`, `results`.

`date` — время формирования ответа сервером в UTC; интерфейс показывает часовой пояс
браузера. `tokens` — сумма фактических `usage.total_tokens`, включая входные и выходные
токены каждого обращения. Модель не генерирует метаданные. API-схемы с запретом лишних
полей опубликованы в `/openapi.json`; сервер и браузер проверяют формат ответа.
Весь текст модели отображается как текст, не HTML.

**Приложение не задаёт ограничений на токены:** в запросах отсутствуют `max_tokens`,
`max_completion_tokens` и `stop`, в промптах нет лимитов длины ответа. Не требуется и
JSON-формат ответа модели. Во всех подходах и на каждом этапе системная инструкция
требует отвечать по-русски, включая созданный промпт и промежуточные результаты,
даже если вопрос или история на другом языке. Синтаксис кода и идентификаторы сохраняются.
В прямом режиме нет дополнительных инструкций по способу решения.
В исходном разделе рассуждения включены, `reasoning_effort` определяется выбранной
верхней вкладкой, явная температура не отправляется. Только температурная ветка
отключает рассуждения: при включённом thinking DeepSeek игнорирует temperature.
Пошаговый режим дополнительно запрашивает объяснение решения в обычном ответе:
внутренний `reasoning_content` не подменяет итог и не сохраняется в истории.
Собственные ограничения длины генерации, контекста и квоты у
провайдера остаются. Оборванная генерация, пустой ответ, отсутствие достоверной
статистики и ошибки внутри HTTP 200 не выдаются за успешный ответ.

Ожидание одного обращения к провайдеру — до 180 секунд без сетевой активности,
всего запроса в браузере — до 10 минут. Это сетевые тайм-ауты, а не лимиты токенов.
Сервер не хранит диалоги между запросами: контекст приходит из браузера. Ключ API
остаётся только на сервере. Приложение сохраняет ограничение частоты: 10 пользовательских
запросов в минуту на процесс; сравнение считается одним запросом приложения, но
использует до семи обращений к провайдеру.
