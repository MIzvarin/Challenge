# question-api Specification

## Purpose

Возможность фиксирует существующий HTTP-контракт отправки задачи и проверки состояния приложения. Она определяет допустимые входные данные, метаданные результата, ошибки и ограничения частоты запросов.

## Requirements

### Requirement: Вопрос и параметры запроса
`POST /api/ask` SHALL принимать непустой строковый `question` с удалением крайних пробелов, `mode` из `direct`, `steps`, `prompt`, `roles`, `compare`, `effort` из `low`, `max` и UUID `conversation_id`. По умолчанию SHALL использоваться `direct`, `low`, пустая история и новый UUID на запрос; верхнего ограничения длины вопроса приложение SHALL не задавать.

#### Scenario: Запрос только с вопросом
- **WHEN** клиент отправляет `{"question": "  Привет  "}`
- **THEN** сервер обрабатывает вопрос `Привет` в режиме `direct` с effort `low`, без истории и с новым UUID

#### Scenario: Недопустимые входные данные
- **WHEN** вопрос отсутствует, пуст после обрезки, имеет неверный тип, либо переданы неизвестный mode, effort, невалидный UUID или лишние поля
- **THEN** сервер возвращает HTTP 422 с безопасным строковым `detail` без обращения к провайдеру

#### Scenario: Длинный вопрос
- **WHEN** клиент отправляет допустимый вопрос длиной 20000 символов
- **THEN** сервер передаёт весь вопрос модели без обрезки приложением

### Requirement: Валидация истории запроса
Сервер SHALL принимать `history` как объект с ключами подходов и списками непустых сообщений `user` / `assistant`, идущих завершёнными парами в этом порядке. В одиночном режиме разрешён только ключ выбранного подхода, в сравнении — ключи четырёх подходов; системные сообщения и лишние поля сообщения SHALL отклоняться.

#### Scenario: Допустимое продолжение сравнения
- **WHEN** запрос `compare` содержит отдельные завершённые пары сообщений в `history.direct` и `history.roles`
- **THEN** сервер принимает историю, а отсутствующие истории других подходов считает пустыми

#### Scenario: Неполная или чужая история
- **WHEN** история содержит одиночное сообщение пользователя, обратный порядок ролей, пустой текст, роль `system` или ключ `roles` в режиме `direct`
- **THEN** сервер возвращает HTTP 422 и не вызывает провайдера

### Requirement: Структурированный ответ API
Ответ успешного `POST /api/ask` SHALL содержать только `question`, `date`, `mode`, `effort`, `tokens`, `results`. Каждый результат SHALL содержать `mode`, `answer`, `tokens`, `duration_ms`, `stages`, `error`; каждый этап — `name`, `content`, `tokens`. Сервер SHALL формировать `date` в UTC, отражать обработанный вопрос и выбранные параметры, а числовые счётчики SHALL быть неотрицательными целыми либо явно допустимым `null` при ошибке.

#### Scenario: Ответ одиночного подхода
- **WHEN** допустимый запрос `direct` успешно обработан
- **THEN** HTTP 200 содержит один результат `direct` с непустым ответом, `error: null`, пустыми `stages`, токенами и длительностью
- **AND** `date` является временем формирования ответа сервером с часовым поясом UTC

#### Scenario: Опубликованная схема
- **WHEN** клиент запрашивает `/openapi.json`
- **THEN** схема API описывает обязательные поля ответа, формат `date-time` и запрет дополнительных полей в моделях запроса и ответа

### Requirement: HTTP-ошибки одиночного запроса
Сервер SHALL возвращать строковый `detail` и соответствующий статус для ошибки запроса целиком или одиночного подхода: 422 для неверного ввода, 429 для лимита, 503 для отсутствующего ключа или проблем доступа, 502 для сетевой ошибки либо некорректной генерации, 504 для тайм-аута. Сырые сообщения и метаданные ошибок провайдера SHALL не передаваться клиенту.

#### Scenario: Ключ не настроен
- **WHEN** допустимый вопрос отправлен без серверного API-ключа
- **THEN** сервер возвращает HTTP 503 с указанием настроить `OPENCODE_GO_API_KEY` и не вызывает провайдера

#### Scenario: Сетевая ошибка одиночного решения
- **WHEN** соединение с провайдером завершается ошибкой
- **THEN** одиночный запрос получает HTTP 502 с безопасным сообщением, без частичного ответа модели

### Requirement: Проверка состояния без генерации
`GET /api/health` SHALL возвращать HTTP 200 и `{"status": "ok"}` независимо от наличия API-ключа, без обращения к провайдеру и без расхода квоты генерации.

#### Scenario: Проверка приложения без ключа
- **WHEN** клиент вызывает `/api/health` при ненастроенном ключе
- **THEN** получает `{"status": "ok"}`, но это не подтверждает доступность модели или подписки

### Requirement: Ограничение частоты пользовательских запросов
Сервер SHALL допускать не более 10 запросов генерации за скользящие 60 секунд на процесс приложения, независимо от клиента и подхода. Сравнение SHALL занимать одну позицию лимита приложения; превышение SHALL возвращать HTTP 429 и положительный `Retry-After` до обращения к провайдеру.

#### Scenario: Одиннадцатый запрос за минуту
- **WHEN** десять допустимых запросов с настроенным ключом уже прошли проверку лимита за последние 60 секунд и приходит следующий
- **THEN** сервер возвращает HTTP 429 с числом секунд ожидания в `Retry-After` и не вызывает модель для этого запроса

#### Scenario: Освобождение окна
- **WHEN** с момента учтённого запроса прошло 60 секунд
- **THEN** он больше не занимает позицию лимита

### Requirement: Запрет кэширования API
Сервер SHALL добавлять `Cache-Control: no-store` к ответам на пути `/api/`, включая успешные ответы и ошибки.

#### Scenario: Ответ проверки состояния
- **WHEN** клиент получает ответ `/api/health`
- **THEN** заголовок `Cache-Control` равен `no-store`
