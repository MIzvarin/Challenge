# Design

## Context

Мотивация и границы изменения описаны в `proposal.md`. На момент обследования 6 ноября 2026 года `openspec list --specs --json` возвращает пустой список; существующая функциональность находится в Python-бэкенде и React-интерфейсе, а её описание — в README и инструкции размещения.

Это сквозная документальная фиксация контрактов нескольких подсистем. Дизайн нужен для разграничения возможностей, сохранения нюансов безопасности и переноса первоначальной базы в основные спецификации без изменения приложения.

### Наблюдаемая архитектура

```text
Browser UI + localStorage
        |
        | /api/ask + history + conversation_id
        v
Backend: validation + rate limit + strategies
        |
        | chat/completions + server key + session ID
        v
OpenCode Go --> DeepSeek
```

В разработке между браузером и бэкендом находится прокси dev-сервера; в собранном варианте бэкенд раздаёт фронтенд самостоятельно. Сервер не восстанавливает историю по session ID: сообщения передаются в каждом запросе. Версии Python 3.15.2 и React 19.3.0 взяты из файлов проекта, а не из проверки установленного окружения или внешнего каталога релизов.

## Goals / Non-Goals

**Goals:**
- Разделить контракты на шесть устойчивых областей с самостоятельными `Purpose`, требованиями и сценариями.
- Сохранить различия между ошибкой одиночного запроса и частичной ошибкой сравнения, локальной историей и внешней сессией, постоянным хранением и работой только в памяти.
- Сделать путь от требования к исходнику или существующей проверке явным, не закрепляя имена внутренних функций как контракт.

**Non-Goals:**
- Не объявлять желаемое поведение реализованным: инструкция русского языка не гарантирует послушание модели, отмена ожидания не гарантирует остановку внешней генерации, health не подтверждает доступ к Go.
- Не описывать черновики как сохраняемые после перезагрузки: они изолированы только в памяти открытого интерфейса.
- Не считать описание Docker доказательством успешной сборки образа или фактического развёртывания на VPS.

## Decisions

### 1. Первичная база через обычное изменение

Создать шесть delta-спецификаций с `ADDED Requirements`, хотя функции уже существуют. Здесь добавляется первое формальное описание, а не новый код. У каждой новой возможности есть содержательное `Purpose`, которое переносится в основной файл без TBD.

Альтернатива — сразу написать основные спецификации без изменения — не даёт согласованного набора предложения, решений и проверяемых задач. Отказ от спецификаций как для обычной правки документации тоже не подходит: цель запроса — создать отсутствующую базу контрактов.

### 2. Источники и границы возможностей

| Возможность | Основные источники | Существующие проверки |
| --- | --- | --- |
| `solving-strategies` | `backend/app/solver.py` | `backend/tests/test_modes.py`: этапы, история, сравнение, effort, язык, частичные ошибки |
| `question-api` | `backend/app/schemas.py`, `backend/app/main.py` | `backend/tests/test_api.py`, `backend/tests/test_modes.py`: формат, статусы, лимит, OpenAPI |
| `model-integration` | `backend/app/opencode_go.py`, `backend/app/solver.py` | те же backend-тесты: HTTP-заглушки, сессии, параметры, статистика, отказы |
| `conversation-history` | `frontend/src/conversations.ts`, `frontend/src/conversation-store.ts` | одноимённые `.test.ts` и `frontend/src/App.test.tsx`: миграция, поколения, гонки и очистка |
| `web-interface` | `frontend/src/App.tsx`, `frontend/src/api.ts`, `frontend/src/modes.ts`, `frontend/src/components/` | `frontend/src/App.test.tsx`, `frontend/src/api.test.ts`: взаимодействия, проверка ответа и безопасный текст |
| `deployment` | `backend/app/config.py`, `backend/app/main.py`, `frontend/vite.config.ts`, `Dockerfile`, `.dockerignore`, `scripts/package-deploy.sh`, `docs/deploy.md` | `backend/tests/test_api.py`: настройки и недоступность секретных файлов; остальное проверяется чтением конфигурации |

При расхождениях документации и реализации as-is основывается на исходниках с подтверждением тестами, а не на добавлении желаемой функции. Существенных блокирующих противоречий при обследовании не выявлено. README используется как обзор, но не копируется целиком; внутренние алгоритмы остаются в этом дизайне и коде, а спецификации описывают наблюдаемые контракты.

Альтернатива — одна большая спецификация — смешивает независимые области и затрудняет будущие небольшие изменения. Детализация каждого компонента интерфейса отдельной возможностью, напротив, избыточна для размера проекта.

### 3. Явные условия надёжности и безопасности

Постоянное хранение и согласование вкладок описываются при доступных `localStorage` и Web Locks. Общая блокировка сериализует изменения, отдельные блокировки обозначают активные запросы, а UUID поколения проверяется перед применением результата. UUID5 с именем `effort:mode:strategy` формирует внешний session ID; это механизм текущего кода, а контракт требует стабильности и изоляции, не конкретной функции вычисления.

Для отсутствующих Web Locks и отказа записи описан существующий режим памяти с предупреждением. Для очистки различаются локальные данные приложения и данные внешнего провайдера. Размещение ограничено существующей приватной схемой SSH, без подразумеваемой встроенной авторизации.

Альтернатива — безусловные обещания синхронизации, удаления у провайдера или сохранения истории — не соответствует реализации и создала бы скрытые задачи разработки.

### 4. Документация и согласованное уточнение селектора теста

После отдельного запуска apply перенести все шесть delta-файлов в основные спецификации через workflow sync: получить актуальные status и specs-инструкции, использовать разрешённые ими пути, сохранить `Purpose`, заменить секцию операций единым `## Requirements`. Основной формат — `# <capability> Specification`, `## Purpose`, `## Requirements`.

В README заменить только утверждение «начальные спецификации ещё не перенесены» на перечень ссылок на основные возможности. Не переписывать инструкцию запуска и не менять код приложения, зависимости, Dockerfile или конфигурацию OpenSpec. После переноса изменение остаётся активным; архивирование — отдельный запрос.

При проверке обнаружено, что HTML-тест в `frontend/src/App.test.tsx` ищет текст вопроса по всему документу: до очистки черновика он одновременно присутствует в абзаце переписки и textarea. Пользователь отдельно согласовал ограничение этого запроса селектором `p`, как в соседнем тесте вопроса. Остальные проверки, включая отсутствие элементов `script`, `img`, `iframe`, сохраняются. Это устраняет неоднозначность теста, не меняя требования, приложение или порядок его асинхронных обновлений.

Альтернатива — копировать delta-файлы как есть — оставляет операционные заголовки в основных контрактах. Автоматическое архивирование заодно с переносом выходит за подтверждённый объём.

## Risks / Trade-offs

- [Снимок устаревает при следующем изменении кода] → будущие изменения уточняют соответствующую возможность; даты обследования и ссылки на источники остаются здесь, а не становятся требованиями.
- [Прохождение структурной валидации ошибочно принимается за доказательство поведения] → отдельно проверить соответствие кодом и тестами; явно сообщать, какие команды действительно выполнялись.
- [Проверки требуют недоступного локального runtime] → не менять версии ради запуска, не устанавливать зависимости без отдельного согласования; зафиксировать конкретный блокер и не отмечать проверку выполненной.
- [Внешний сервис ведёт себя иначе, чем ожидает клиент] → специфицировать отправляемые параметры и проверку ответа, не гарантировать качество решения; не вызывать реальную модель при проверках.
- [Размещение описано шире автоматических тестов] → отличать проверку существующих конфигураций от запуска Docker, VPS и SSH; такие операции в это изменение не входят.

## Migration Plan

1. Проверить согласованные delta-спецификации и текущие основные файлы, затем синхронизировать шесть возможностей без изменений приложения.
2. Обновить строку README и ссылки на созданные спецификации.
3. Выполнить строгую валидацию основных спецификаций и изменения; запустить существующие backend/frontend-тесты, lint и сборку при доступном окружении, без внешней модели.
4. Проверить итоговый diff: только документы и согласованное уточнение одного селектора HTML-теста. Не отмечать непроведённые проверки как успешные и не архивировать изменение автоматически.

Выкладка приложения, миграция пользовательских данных и перезапуск сервиса не требуются. Откат при необходимости — отдельное удаление только созданных этим изменением документов и возврат только собственных правок README и селектора теста после проверки diff; код приложения и чужие изменения не затрагиваются.
