# Design

## Context

Мотивация — `proposal.md`, требования — четыре delta-spec в `specs/` этого изменения.

Наблюдаемое состояние:
- `backend/app/opencode_go.py` и `responses_go.py` валидируют только `usage.total_tokens` и возвращают `(answer, tokens)`. Детализация не сохраняется. `solver.py` агрегирует токены вызовов, сохраняет этапы и возвращает null общего расхода при ошибке сравнения.
- В `schemas.py` ответы/результаты/этапы запрещают лишние поля. `frontend/src/api.ts` проверяет точное число полей, а `conversations.ts` использует тот же валидатор при восстановлении. Простое добавление cost сломает чтение истории и сетевых ответов без согласованного обновления.
- `AnswerPanel.tsx` — общий компонент всех карточек. Истории 13 исходных диалогов и трёх моделей сохраняются раздельно в существующих ключах, store обеспечивает блокировки и поколение.
- Завершённое, но не архивированное `add-model-comparison-workspace` уже реализовано в коде. Основные specs ещё не включают его model-comparison и изменения меню/истории. Новое изменение опирается на фактический набор DeepSeek/Kimi/Grok/GPT, не возвращает прежние модели и не повторяет сброс истории. Перед архивированием этой работы нужно сначала синхронизировать или архивировать предыдущее изменение, затем проверить совместимость дельт.
- Read-only проверка 2026-11-08: каталог `https://opencode.ai/inference/go/v1/models` содержит `cost.text`, context overrides и временные multipliers; `https://opencode.ai/docs/go/#usage-limits` подтверждает USD за 1M токенов. Генерация не вызывалась. Это опубликованные API-ставки сервиса, не доказательство цены прямого API производителя или реального списания Go.

## Goals / Non-Goals

**Goals:**
- Общий денежный конвейер поверх двух адаптеров с сохранением прежних правил успешной генерации и счётчика tokens.
- Детерминированные расчёты без сети тарифов в пути запроса; пригодные для тестов часы и десятичная арифметика.
- Аддитивное расширение истории без разрушительной миграции.

**Non-Goals:**
- Интерпретация `opencode.allowance` как денег, реально списанных с пользователя; автоматическая тарификация аккаунта.
- Универсальный интерпретатор всех будущих схем тарифов, произвольных моделей или мультимодального usage.
- Изменение сообщений модели, маршрутизации, числа вызовов, лимитов, режимов рассуждения и обработки HTTP-ошибок.

## Decisions

### 1. Версионированный серверный снимок тарифов

Добавить `backend/app/pricing.py` с проверяемыми данными для четырёх точных ID, версией `opencode-go-2026-11-08-v1` и HTTPS URL источника. Начальные ставки USD/1M токенов:

| ID | Обычный вход | Кэш чтение | Кэш запись | Выход | Условия |
| --- | ---: | ---: | ---: | ---: | --- |
| deepseek-v4.1-flash | 0.15 | 0.003 | — | 0.60 | Все ставки ×2 пн–пт 01:00–04:00 и 06:00–10:00 UTC |
| kimi-k2.7-code | 0.95 | 0.19 | — | 4.00 | Без порога |
| grok-4.7 | 2.00 | 0.50 | — | 6.00 | При входе >200000: 4.00 / 1.00 / — / 12.00 |
| gpt-6-luna | 0.10 | 0.01 | 0.125 | 0.50 | При входе >272000: 0.20 / 0.02 / 0.25 / 0.75 |

Каждый вызов получает фактический ID из уже выбранного серверного маршрута и время начала в UTC; кэшированный вход входит в проверяемый размер входного контекста. Временные интервалы полуоткрытые, конец не включается. Для пользовательского `OPENCODE_GO_MODEL` без точного совпадения — null, без эвристики названия. Перепроверить снимок по публичному источнику при реализации, изменение ставок оформлять новой версией.

Альтернативы: загрузка каталога на каждый вопрос создаёт сетевую зависимость и изменяет старые результаты; единая ставка на total_tokens неверна; ставки прямых производителей могут не описывать конкретный Go ID. Снимок требует ручного обновления, зато воспроизводим и явно назван.

### 2. Нормализация usage без ослабления проверки ответа

Вынести внутреннюю структуру результата вызова в отдельный модуль, например `backend/app/usage.py`: текст, total_tokens и nullable нормализованная детализация. Chat Completions читает `prompt_tokens`, `completion_tokens`, `prompt_tokens_details.cached_tokens`, а также подтверждённые DeepSeek cache-hit/cache-miss поля. Responses читает `input_tokens`, `output_tokens`, `input_tokens_details.cached_tokens`; категории записи кэша принимать только из документированного соответствующего поля, не угадывать по названию.

Политика нормализации:
- Строгие неотрицательные целые, boolean не число. Вход включает кэш; нормализованные категории обычного входа, чтения и записи непересекающиеся. Если документированный протокол задаёт иные включения, адаптер приводит их к этому виду.
- Проверять равенство total_tokens сумме входа и выхода для поддерживаемых протоколов, размер кэша и согласованность дублирующих полей. Токены reasoning — подмножество выходных, не отдельное слагаемое.
- Отсутствующую категорию можно считать нулём только если это следует из документированного контракта конкретного протокола. Если необходимые cache-детали отсутствуют и контракт не устанавливает нулевое значение — цена null. Если два подтверждённых поля противоречат друг другу — также null. Не угадывать вход по тексту или отношению total_tokens.
- Старые ошибки отсутствия/невалидности total_tokens, незавершённого и пустого ответа остаются ошибками. Ошибки лишь дополнительных данных цены дают null cost, не HTTP 502 и не повтор генерации.

Альтернатива — сделать полную детализацию обязательной для успеха — отвергнута: потеря ответа ради вспомогательной метрики нарушает согласованную деградацию. Прямое использование поля cost провайдера также не выбрано: оно может означать allowance, а нужна воспроизводимая оценка.

### 3. Десятичная цена и единый контракт

Внутри использовать стандартный Python Decimal и выражение `(обычный_вход × ставка + кэш_чтение × ставка + кэш_запись × ставка + выход × ставка) / 1000000`, с применимым временным множителем. Достаточная локальная precision исключает округление для поддерживаемых тарифов и счётчиков до суммирования; строка без экспоненты сериализуется без двоичного float.

В `schemas.py` добавить строгий объект Cost: `amount: str`, `currency: Literal['USD']`, `pricing_version: str`, `source: str` с валидацией HTTPS URL. `amount` соответствует `^(0|[1-9][0-9]*)(\.[0-9]+)?$`; без пробелов, знака, экспоненты и лишних полей. Обязательное поле `cost: Cost | None` добавить на три уровня. Один снимок тарифов на обработку запроса позволяет суммам иметь единые version/source.

`solver.py` оценивает каждый фактический вызов, суммирует только стоимость вызовов подхода; этап хранит свою цену, но не добавляется к уже накопленному итогу ещё раз. Неизвестный вызов делает полный итог null. Ошибка подхода даёт null независимо от уже известных этапов; общий compare cost null, если неизвестен любой результат. Одиночная HTTP-ошибка по-прежнему не создаёт фиктивный успешный ответ с ценой.

Альтернатива — JSON number — проще, но приводит к потере десятичной точности и расхождениям при клиентской проверке сумм.

### 4. Разделить сетевую и историческую совместимость

Расширить `frontend/src/api.ts` типом Cost и общими проверками. Новые сетевые ответы требуют cost на каждом предусмотренном уровне; точные allowlist полей остаются строгими. Для чтения истории добавить явный режим legacy либо отдельный вход в валидатор: отсутствие cost допустимо, присутствующий объект проверяется полностью. Не делать отсутствующую цену автоматически допустимой во всех сетевых ответах.

Проверять суммы без Number: разобрать десятичные строки в целое значение и масштаб через BigInt, выровнять масштабы для сравнения/сложения. Известный итог равен точной сумме результатов и не существует при неизвестном результате. Для одного запроса проверять единые version/source; цены разных прошлых вопросов могут иметь разные версии. Итог результата не меньше суммы известных промежуточных этапов; недостающий финальный вызов из текста не восстанавливать.

В `conversations.ts` сохранять полученный объект без пересчёта, не менять ключи, UUID, marker ревизии или набор scopes. Старые поля можно оставить отсутствующими в памяти либо нормализовать в null при чтении; оба пути должны одинаково отображаться и не требовать очистки. `buildHistory` по-прежнему формирует только текст.

Альтернатива — новая ревизия с полным сбросом — не нужна и не разрешена; единый permissive валидатор для сети и истории скрывал бы несовместимый релиз.

### 5. Представление без обещаний биллинга

Добавить переиспользуемое форматирование десятичных строк: русская локаль, до 6 знаков после запятой, явный USD и приблизительность, положительные значения <0.000001 показывать через нижнюю границу отображения, ноль только для нулевого amount. В `AnswerPanel.tsx` строка стоимости рядом с токенами каждого результата и этапа, итог compare рядом с итоговыми токенами. Сведения о тарифе — доступный `details` с версией и ссылкой, не tooltip-only; пояснение «Оценка по опубликованным API-тарифам; не фактическое списание Go».

Альтернатива — две дробные цифры как для обычной валюты — скрыла бы почти все маленькие расходы; пересчёт на клиенте сделал бы историю нестабильной.

## Risks / Trade-offs

- [Go может не отдавать достаточные cache-детали] → Не выдумывать ноль; сохранить ответ и показать недоступность. Проверить публичную документацию сопоставления полей и использовать обезличенные fixtures, не оплаченные диагностические вызовы.
- [Снимок устаревает] → Версия/дата/ссылка доступны пользователю, обновление только новым снимком; история неизменна.
- [Время начала и биллинговое время могут различаться на границе peak] → Явно приблизительный расчёт, фиксированная UTC-политика и граничные тесты, без обещания совпадения со списанием.
- [Строгие старые клиенты не принимают новые поля] → Согласованный релиз и перезагрузка всех вкладок, разделение legacy history и нового API.
- [Несинхронизированная предыдущая работа] → Не переписывать её артефакты; перед архивированием применить baseline предыдущего изменения и перепроверить эту дельту.
- [Повреждённые сохранённые денежные данные] → Прежняя безопасная деградация истории, без автоматической перезаписи или молчаливого игнорирования.

## Migration Plan

1. Перед реализацией согласовать артефакты с пользователем. Добавление цены не меняет текущую ревизию истории и не даёт разрешения удалять данные.
2. Реализовать backend, frontend и контрактные тесты одним согласованным релизом. Документировать новый JSON, тарифную основу и ограничение совместной работы старых/новых вкладок.
3. Проверить восстановление старой и смешанной истории в обоих ключах; после развёртывания перезагрузить все вкладки. Проверка без реальной генерации допустима через health и статический интерфейс; платные проверки не автоматизировать.
4. Откат backend/frontend выполняется парой. Старый frontend со строгим валидатором не обязан читать новые поля истории: не очищать её автоматически и не обещать совместимый откат; хранить локальную копию при необходимости, возвращение новой версии восстановит совместимое чтение. Удаление переписки не является способом миграции.
5. До архивации согласовать порядок с `add-model-comparison-workspace`, затем проверить все OpenSpec-дельты.
