# Design

## Context

Мотивация и границы — в proposal.md. Первая версия раздела уже реализована: Beam/Kimi через `complete()`, Gemini через `google_go.py`, отдельный `/api/ask-models`, 16 scopes, общий контроллер и две группы хранения. Старые 13 диалогов находятся в v3, три модельных — в `challenge.model-comparisons.v1`. Проверки чтения и записи разделены: сохранение одной группы не скрывает предупреждение о повреждении другой. Эти гарантии необходимо сохранить после однократного сброса.

Публичный каталог https://opencode.ai/inference/go/v1/models повторно проверен 8 ноября 2026: `kimi-k2.7-code` предоставляет Chat Completions, `grok-4.7` и `gpt-6-luna` — Responses на `https://opencode.ai/inference/go/openai/v1`. GPT и Kimi не поддерживают temperature. Доступность в каталоге не подтверждает квоту ключа; генерация при планировании не вызывалась. Пользователь разрешил удалить всю локальную историю, включая исходные разделы и Kimi, вместо переноса диалогов исключаемых моделей.

## Goals / Non-Goals

**Goals:** сохранить контракты существующих endpoint и взаимодействие чата; заменить модельный allowlist и протоколы; однократно и согласованно сбросить всю историю; после сброса сохранять новые диалоги и прежние гарантии изоляции, блокировок и предупреждений.

**Non-Goals:** универсальный LLM-шлюз, динамическая загрузка каталога в рантайме, потоковая выдача, автоматическое сравнение моделей и гарантированное отключение их внутренних рассуждений. Выбранная модель использует стандартные настройки генерации Go.

## Decisions

### 1. Отдельный endpoint, а не расширение `/api/ask`

Сохранить `POST /api/ask-models` со строгими моделями запроса и ответа из delta `model-comparison`. Запрос содержит question, обязательный model из нового allowlist, необязательные conversation_id и history.direct только выбранного диалога. Нет входных mode, effort и temperature. Отсутствующий conversation_id получает UUID, как старый API. Маршрут использует тот же RateLimiter и проверку ключа: один вопрос — один вызов и одна позиция лимита. Старые beam-free и gemini-4-argon отклоняются с 422 до генерации.

Успешный ответ сохраняет структуру прямого ответа: question, date, mode direct, effort null, tokens, results с единственным прежним результатом direct, пустыми stages и error null; дополнительно обязательный model, без temperature. Это позволяет переиспользовать карточку «Ответ», не выдавая выбор модели за настройку effort. Ошибки — соответствующий HTTP-статус со строковым detail, не результат внутри HTTP 200.

Альтернатива — ещё одна ветка существующего union — затронула бы публичные строгие схемы и обработку пяти стратегий без необходимости.

### 2. Kimi через Chat Completions, Grok/GPT через Responses

Реестр содержит `kimi-k2.7-code`, `grok-4.7`, `gpt-6-luna` в таком порядке, имена и протокол. Не расширять `OPENCODE_GO_MODEL`: он по-прежнему относится только к DeepSeek. Не принимать URL или произвольную модель от браузера. Альтернатива замены только ID в Chat Completions не использует нативный протокол двух новых моделей и не проверяет их специфическую структуру завершения.

Kimi использует существующий Chat Completions transport/parser с явным model на вызов, без изменения общего Settings при независимых запросах вкладок. Не передавать DeepSeek generation_parameters; старые вызовы DeepSeek сохраняют свои параметры.

Для Grok/GPT добавить `responses_go.py`: POST `responses` существующего Go OpenAI client с Authorization Bearer из того же Settings, User-Agent, x-opencode-session, model, stream false, store false. Русскоязычную системную инструкцию передавать в instructions, полную историю user/assistant и новый вопрос — в input как текстовые сообщения соответствующих ролей. Не использовать previous_response_id: контекст остаётся явно передаваемым из браузера. Не отправлять temperature, reasoning/effort, max_output_tokens, stop или response_format. Удалить Google-адаптер и его специфические тесты после перевода всех маршрутов и проверок; Kimi/DeepSeek-парсер остаётся.

Responses-парсер проверяет верхний status completed, отсутствие error и завершённость текстовых сообщений assistant в output. В порядке массива объединяются только content-части типа output_text; reasoning не сохраняется и не заменяет итог. Refusal, failed/incomplete, незавершённое сообщение, пустой итог и недостоверный usage.total_tokens — ошибка одиночного запроса. Нулевой целый расход допустим, bool/строки/дроби запрещены. Сохраняются безопасный HTTP-маппинг, тайм-ауты и отсутствие повторов/fallback. Wire-fixtures сверяются с документацией Responses до реализации адаптера; новых SDK не требуется.

### 3. Одна выбранная модель на запрос

Новый solver выбирает адаптер по model, выполняет ровно один прямой ответ и измеряет его длительность. Автоматического fan-out и gather для трёх моделей нет. В провайдер передаются только history.direct выбранной вкладки и новый вопрос. Ошибка провайдера проходит обычным HTTP-путём одиночного запроса; частичных успехов, агрегатных токенов и общего результата трёх моделей нет. Не добавлять автоматический retry или fallback.

Сессии: uuid5(conversation_id, `models:<model-id>:direct`). Старые формулы solver.py не менять. Дефолтные настройки новых моделей не наследуют выбранную температуру или effort других разделов.

### 4. Три вкладки по аналогии с температурой

Сохранить scope `{workspace: models, model, mode: direct}` и три ConversationKey `models:<model-id>:direct`, обновив model ID. Вкладки Kimi K2.7 Code → Grok 4.7 → GPT‑6 Luna используют прежнюю доступную навигацию Tabs; по умолчанию Kimi. Выбор сохраняется в памяти до перезагрузки. Каждая вкладка показывает свою переписку и одну форму; переключение не вызывает API и не отменяет ожидание другой вкладки. Карточка и адаптивная компоновка не меняются.

Расширить типы API и валидатор отдельно от прежних ответов: проверять совпадение выбранного model, единственный результат direct, effort null, отсутствие temperature, stages [], error null и совпадение токенов результата с общим расходом. Переиспользовать карточку «Ответ» с метаданными фактической модели. Не писать «рассуждения отключены»: модели используют стандартные настройки Go.

Контроллер выбирает API по workspace и строит history.direct из успешных пар текущего scope, сохраняя единые abort, generation checks, draft и request lock. Успех очищает только черновик отправившей вкладки; любая ошибка оставляет его. Повторный запрос той же модели заблокирован до завершения, но отдельный пользовательский вопрос другой модели разрешён независимо — как у разных температур. Сам по себе один вопрос никогда не запускает две или три модели.

### 5. Однократный полный сброс по маркеру ревизии

Добавить постоянный маркер `challenge.conversations.revision` со значением `kimi-grok-luna-v1`. При несовпадении маркера новая версия до загрузки старых данных выполняет под общей history Web Lock очистку ключей challenge.conversations.v1/v2/v3 и challenge.model-comparisons.v1, смену generation и сброс памяти/черновиков/ожиданий. Маркер записывается последним, только после успешной очистки и записи нового UUID. При двух запускающихся вкладках сброс выполняется однажды. Использовать общий внутренний helper очистки без повторного захвата той же блокировки.

Не загружать прежний контекст даже на первый кадр: начальный снимок пустой, первый locked refresh завершает проверку ревизии до допуска отправки. Отдельный флаг инициализации блокирует форму, пока проверка не завершена. При недоступном хранилище или отсутствии Web Locks до подтверждённой ревизии разрешён только новый пустой диалог в памяти с предупреждением, без записи общей истории и маркера. Неуспешная запись маркера не выдаётся за завершённую миграцию; при следующем запуске попытка сброса повторяется. При нескольких вкладках все новые версии проверяют ревизию под тем же lock перед чтением/записью.

После маркера формат v3 остаётся для 13 исходных scopes, модельный ключ — для нового набора из трёх ID. Новые данные переживают перезагрузки. Обычная общая очистка удаляет четыре ключа истории, меняет generation и сохраняет revision, поэтому повторного автоматического сброса нет. Пользователь разрешил удаление, поэтому альтернатива переноса Kimi и скрытого архива Beam/Gemini отклонена; не нужны новый формат v4 или постоянный архив. Сохранение прежних данных при этом обновлении намеренно не гарантируется.

Снимок общего store включает обе группы, читает их под прежней общей Web Lock и проверяет единый generation. Писать только изменённую группу, чтобы ошибка новой записи не удаляла и не переимпортировала старую историю. Добавить новый ключ в storage-события и общую очистку; резервировать каждый модельный scope отдельно, trackRequest сохраняет активное ожидание других вкладок. Проверять модельные turns отдельным валидатором с совпадением model и scope; ошибка нового ключа не скрывает старую группу. При отказе записи действуют прежние предупреждение и режим памяти. Два ключа не являются транзакцией localStorage: общая очистка остаётся best-effort при исключениях, а generation блокирует применение старых результатов.

## Risks / Trade-offs

- [Responses имеет другой формат завершения] → wire-fixtures и parser-тесты для completed, incomplete/failed, refusal, reasoning, usage и ошибок внутри HTTP 200.
- [Смешивание истории при переключении модели] → отдельные scopes, черновики и контексты, проверка model ответа; тесты фонового ответа после перехода в другую вкладку.
- [Потеря прежней переписки] → явно описать разрешённый пользователем полный сброс, маркер и отсутствие переноса; после миграции проверять сохранение новых сообщений повторной перезагрузкой.
- [Старые открытые сборки могут записать старый набор после сброса] → обновить все вкладки перед работой; generation запрещает поздние ответы старого поколения, но совместная эксплуатация разных сборок не поддерживается.
- [Сбой localStorage между операциями] → раздельные записи, предупреждение, сохранение доступных копий и проверки поколения; не обещать атомарную запись разных ключей при отказе браузера.

## Migration Plan

1. Развернуть backend с новым allowlist и Responses-адаптером, сохранив существующий ключ и старый `/api/ask`. Старый frontend с Beam/Gemini временно получит 422 до обновления.
2. Развернуть frontend, перезагрузить все вкладки. Первый запуск новой ревизии очищает всю локальную переписку, меняет UUID и записывает маркер; до завершения проверки старые сообщения не используются.
3. Тестами без генерации проверить сброс при старых v1/v2/v3 и модельной истории, конкурирующие запуски, ошибку хранилища, отсутствие Web Locks, защиту от старого ответа, а также сохранение новых диалогов на повторном запуске. Обновить README и docs/deploy.md.
4. Откат к прежней сборке не восстанавливает удалённую историю и не гарантирует чтение нового набора model ID. Перед откатом очистить новую историю штатной кнопкой при необходимости; повторное обновление с сохранённым revision не выполняет новый сброс. Откат только backend без frontend не поддерживается для нового набора.
